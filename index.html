This set of excercises grew from a capstone project that I lead with students from Emory University’s MSBA program. In that case we applied machine learning techniques to predict monthly mortgage prepayment (defined below). The original problems were designed to familiarize the group with basic mortgage concepts under somewhat idealized conditions. That content stopped at problem 10. I have since added or updated topics regarding basic fixed rate bonds, forward curve calibration, prepayment, and Monte Carlo pricing. This a work in progress. Eventually we will cover trinomial lattices, PCAs, C++, etc.

Clean Code

There are many excellent books on writing clean code, and I recommend reading a few. However, here are some key principles to get you started.

  • Put most of your logic in python modules and create a single top layer application called demo.py to demonstrate the functionality.
  • Use well named variables. They make the code easier to read and reduce the amount of documentation required.
  • Validate your input to ensure it meets expected ranges or conditions—such as checking that a divisor isn’t zero or a stock price is non-negative—while keeping performance in mind. These checks help catch hard-to-find errors and keep functions reliable without unnecessary slowdowns.
  • Avoid global variables with the possible exception of constants.
  • Strive for clarity and maintainability even if it increases runtime slightly. Pretend you are going to hand this code off to someone else. If you are the only one who knows the code it will hinder your career advancement.
  • Avoid premature optimization. Let your profiler guide you to the code that truly needs to run faster.
  • Consider another programmer who might use your code in the future. Is the API well documented? Does it feel like a natural interface?
  • Do not use magic numbers or strings. Put them in variables. There are three big benefits:
    • The code is more readable.
    • If you need to change the values, you can do it in one place. Imagine your team decided to change the estimate of Pi from 3.14 to 3.14159. It is much easier to change PI = 3.14 to PI = 3.14159 in one place than looking through your entire code base for all occurrences of 3.14
    • If you make a typo in a magic number, your compiler/interpreter will not catch it. The interpreter will complain in the case of a mistyped variable name
  • Do not copy and paste code. If you find yourself tempted to do so, take the opportunity to refactor the shared logic into a separate function. This approach offers similar benefits to avoiding magic values—it promotes clarity, consistency, and maintainability. Trust me, having to comb through a sprawling codebase to locate and update duplicated logic is an absolute nightmare. Save yourself (and others) the trouble by keeping your code DRY (Don’t Repeat Yourself).
  • Do not combine IO and logic. Keep the code that gathers or reports data separate from the code that implements business logic. It is better for the IO code to wrap up its data into structures that aren’t dependent on a particular IO source, and pass those structures to business logic.
  • Use unit tests. As you progress through the problems you will find you need to make significant changes to your existing code. The only way to be confident in fundamental updates is to have a suite of tests to make sure you haven’t broken something unexpected. Testing also tends to make your code cleaner because it naturally leads to the separation of IO and logic. Some developers even write tests before writing the logic
  • Minimize function length. It is very difficult to understand a function with hundreds of lines. Try to break it up into smaller functions for clarity. My rule of thumb is to keep them no longer than a page.
  • Try not to compute the same thing twice. For instance, if your date grid isn’t changing but your rates are, make sure the date grid is computed outside of any loops. This should increase your computational efficiency and code clarity.
  • Leverage vectorization. Python loops are very slow, but you can avoid them by working on an entire vector or matrix at a time via libraries such as NumPy.
  • Think like a mathematician. Applying basic calculus to some of the problems below will make your code cleaner and faster.
  • Keep track of units. Are the units decimal or percent? Not knowing this can lead to a ton of mistakes.
  • Use docstrings. I prefer NumPy’s version.

Large Language Models

Do not overuse LLMs. The point of this is to learn. Having ChatGPT solve the problems for you isn’t helpful. However they can be incredibly useful as an advanced manual or a documentation rough draft generator. Just don’t use them to write the main logic.

Assumptions

Please review these periodically:

  • All mortgages will be fixed-rate loans with no interest-only periods.

  • Mortgage payments are made on the first of each month, with no partial accruals or defaults.

  • The mortgage amount paid is either the scheduled contractual payment or the full remaining balance plus interest owed. We do not consider the case where the borrower “curtails” by paying more than their payment but less than full payoff amount.

  • A pool of loans consists of contracts that are exactly the same. E.g. they share the same balance, coupon, origination, term, etc.

  • No accrual period will start on a day of month that is greater than 28. This avoids tedious month end issues.

  • There will be no special treatment for holidays and weekends.

  • If your settle date lands exactly at the end of an accrual period, you are not entitled to the cash flow associated with that period.
